## What Is Actually Provable (and What Is Not)

### Tamper-evidence: provable, unconditionally

The claim "it is impossible for the records to be tampered with" is not a theorem — it is a wish. The provable version is:

> **Tamper-evidence theorem.** Given a published root hash `R` and a record `r` with inclusion proof `π`, any modification to `r` that preserves its position in the log produces a record `r'` such that `verify(r', π, R) = false`.

This is provable, and it is what courts actually accept. The mechanisms are well-established:

- **SHA-256 hash chains** (the `uuidna` pattern: 2499 theorems, one order-invariant receipt).
- **Merkle trees with inclusion proofs** (Certificate Transparency, RFC 6962).
- **RFC 3161 trusted timestamps** from a third-party Time Stamp Authority.
- **Append-only logs with third-party witnesses** (Sigstore's Rekor, Google's Trillian).

The formal proof obligation is small and dischargeable: show that the hash function is collision-resistant (a cryptographic assumption, not a theorem), show that the tree construction is deterministic, show that the verification predicate rejects any modified input. The first is an assumption; the second and third are theorems.

### Hack-resistance: provable relative to a threat model and TCB

The claim "it is impossible for the machine to be hacked" is also not a theorem. No system is unhackable in the abstract — SeL4, the most thoroughly verified kernel in existence, does not claim this. What is provable is:

> **Security theorem (conditional).** Under threat model `T`, with trusted computing base `TCB`, and cryptographic assumptions `C`, no adversary in class `A` can violate invariant `I`.

Every word in that sentence is load-bearing:

- **Threat model `T`**: what the adversary can do. Can they read memory? Modify firmware? Physical access? Supply-chain compromise? A proof without an explicit threat model is meaningless.
- **TCB**: what must be correct for the proof to hold. The smaller the TCB, the stronger the claim. The goal is to shrink the TCB until it is small enough to audit by hand — ideally to the kernel, the boot ROM, and the crypto primitives.
- **Cryptographic assumptions `C`**: what must be hard. "No adversary can forge an Ed25519 signature" is an assumption, not a theorem. Name it explicitly.
- **Invariant `I`**: what must hold. "The private key never leaves the TPM." "The audit log is append-only." "The device executes only signed firmware." Each invariant is a separate proof obligation.

The honest claim is: *"We can prove that if the TCB is correct and the cryptographic assumptions hold, then no attack in this class can violate this invariant."* That is the strongest claim anyone can make, and it is what the tool should produce.

## The Court-Admissibility Requirement

This is the part that most formal-methods projects ignore, and it is the part that determines whether the tool is actually useful to a basement inventor.

In U.S. federal courts, electronic records are governed by **Federal Rules of Evidence 901, 902(13), and 902(14)**. Rule 902(13) allows self-authentication of records *generated by an electronic process* if certified by a qualified person. Rule 902(14) allows self-authentication of *data copied from an electronic device* if authenticated by a hash value. The 2017 Advisory Committee Notes state that "hash value" means a value "generated by a computer algorithm... using a one-way cryptographic function."

**This is the design target.** The tool should produce records that satisfy FRE 902(13)/(14) **by construction**:

1. Every record carries a SHA-256 hash.
2. Every record carries an RFC 3161 timestamp from an independent TSA.
3. Every record is included in a Merkle tree whose root is published to an append-only log.
4. The log is witnessed by at least one independent third party.
5. The tool emits a **certification packet** that a non-expert can present to a court: the record, the hash, the timestamp, the inclusion proof, the root hash, and a plain-language statement of what the verification proves.

Daubert admissibility of the underlying cryptographic method is well-established: SHA-256, Merkle trees, and RFC 3161 timestamps have been accepted in U.S. courts for over a decade. The tool does not need to argue for the validity of these primitives; it needs to *apply them correctly and document the application*.

For the security proofs, the situation is different: the court does not need to understand the proof, but it does need to accept that *a proof exists and was checked by a machine*. The LEAP / Lean-Rust pattern applies: the certification packet includes a compact certificate that any third party can re-check with free tools, and the certificate's re-checkability is the admissibility argument.

## The Six Layers, Reframed for Compliance

### Substrate & Kernel: The Compliance Predicate Language

Replace `LegalSource`, `Norm`, `Derivation` with:

- **`ComplianceStandard`**: an inductive type representing a regulatory framework (FCC Part 15, GDPR, NIST SP 800-53). Each standard is a *structured object*, not a text blob.
- **`Requirement`**: an individual obligation within a standard ("emissions below X dBm in band Y", "personal data encrypted at rest", "access logged with identity, timestamp, and resource").
- **`Evidence`**: a machine-checkable artifact that discharges a requirement (a test result, a configuration snapshot, a cryptographic attestation).
- **`Assessment`**: a derivation tree showing that a set of evidence discharges a set of requirements.

The kernel-level property is the same as before: **no axioms**. Every requirement is defined inductively; every evidence type has a verified checker; every assessment is a proof term.

### Verification Pipeline: Evidence Generation and Checking

- **Property-based testing** on the evidence checkers (does the configuration parser accept all valid configurations? does the log checker reject any modified entry?).
- **Differential testing** between the Lean checker and the deployed checker (which may be in Rust or C for embedded use).
- **Cold-build + axiom audit + proof-health report** as before, with the trust policy expressed as "no custom axioms; permitted crypto assumptions listed explicitly."

### Tooling: A Compliance DSL

The DSL should let the inventor write:

```
STANDARD FCC-Part-15.247
REQUIRE emission_power(band=2.4GHz) < 1W
REQUIRE emission_power(band=5GHz) < 1W
REQUIRE frequency_hopping(min_channels=15)

EVIDENCE test_report(lab="ABC Labs", date=2026-09-15, hash=sha256:...)
DISCHARGE emission_power(band=2.4GHz) BY test_report.section_3
...
```

And the tool should elaborate this to Lean terms, produce the assessment tree, and emit the certification packet. The `verity_contract` macro pattern is exactly right here: one surface syntax, two artifacts (the EDSL value and the compilation model), one bridge theorem.

The agentic prover's role is different than in the jurisprudence framing: it does not prove legal theorems; it **fills in the evidence gaps**. Given a requirement and a partially completed evidence set, it identifies what additional evidence is needed and either retrieves it from the inventor's records or flags it as missing.

### Governance & Provenance: The Tamper-Evident Ledger

This is the layer that directly serves the court claim. Every artifact — design doc, test result, config snapshot, firmware hash, assessment, certification packet — is:

1. **Hashed** (SHA-256).
2. **Timestamped** (RFC 3161).
3. **Included in a Merkle tree** whose root is published to an append-only log.
4. **Witnessed** by an independent third party (a public transparency log, a notary service, or a peer inventor's node).

The ledger is the **chain of custody**. A court does not need to trust the inventor; it needs to verify that the record presented is the record that was committed at the claimed time. The Merkle inclusion proof does this in a few kilobytes.

### Integration: How a Regulator Verifies

The regulator — FCC inspector, FDA auditor, state AG — should be able to verify a certification packet **without installing the inventor's toolchain**. This is where the WASM build and the replay façade matter most:

- A browser-based verifier that accepts the packet, recomputes the hashes, checks the Merkle proof against the published root, verifies the RFC 3161 timestamp, and reports pass/fail.
- A command-line verifier (`lexlean-verify`) that does the same, for regulators who prefer scripts.
- A one-page plain-language explanation of what the verification proves and what it does not prove.

The Prism-style façade applies here too: the inventor depends on `LexLean` alone; the regulator depends on `lexlean-verify` alone; neither needs to know the internal module structure.

### Observability & Security: Runtime Monitors and Attack Detection

For the **device** (not just the records), the observability layer becomes a **runtime attestation and intrusion-detection system**:

- **Boot-time attestation**: the device measures its firmware, kernel, and application hashes against the signed manifest. Any deviation is recorded and reported. The measurement is anchored in a TPM or TEE.
- **Runtime invariant monitors**: the device checks that its security invariants hold (e.g., "the private key never leaves the TPM", "no unsigned firmware is executing", "the audit log is append-only"). Violations are recorded to the tamper-evident ledger before the device halts.
- **Remote attestation**: the device can prove to a remote verifier that it is running the expected software, using the TPM's endorsement key. This is what makes "the machine cannot be hacked" defensible: the verifier does not trust the device; it trusts the TPM's attestation, which is a hardware root of trust.

The security audit module here is a **proof-of-invariant checker**: it prints the axiom profile of every security-critical function, flags deviations from the trust policy, and emits a replayable receipt that a third party can re-check.

## Day-1 Toolkit (What a Basement Inventor Can Actually Run)

A minimal, usable toolkit in one week:

1. **`lexledger`** — a command-line tool that takes a file, computes its SHA-256, submits it to a free RFC 3161 TSA (e.g., DigiCert, Sectigo, FreeTSA), appends it to a local Merkle tree, and prints an inclusion proof.
2. **`lexverify`** — a browser-based verifier that accepts a ledger entry, re-computes the hash, checks the timestamp, and verifies the Merkle proof against a published root.
3. **`lexcomply`** — a DSL compiler for compliance standards, pre-loaded with FCC Part 15, GDPR Art. 32, and NIST SP 800-171 as starter libraries. Outputs a Lean assessment tree.
4. **`lexattest`** — a TPM-based remote attestation tool for the device, producing signed measurements that can be included in the ledger.
5. **`lexpacket`** — a certification-packet generator that assembles a record, its hash, its timestamp, its inclusion proof, its assessment tree, and a plain-language explanation into a single PDF + JSON bundle.

None of these require Lean on the inventor's machine. The Lean formalization is the **backing proof**: it establishes that the checkers are correct, and it produces the certificate that the packet includes. The inventor runs the tools; the tools carry the proofs.

## Honest Limits

I want to be explicit about three things the tool cannot do, because over-claiming is the fastest way to lose in court:

1. **It cannot prove "impossible to hack" in the abstract.** It can prove "no attack in class A violates invariant I, assuming TCB T and crypto assumptions C." The threat model must be written down and the TCB must be minimized and auditable. If the TCB is a million lines of Linux kernel, the proof is weak. If the TCB is a formally verified microkernel plus a TPM plus a signed bootloader, the proof is strong.

2. **It cannot prove the cryptographic primitives are secure.** SHA-256 collision-resistance and Ed25519 unforgeability are assumptions, not theorems. The tool should name them explicitly and cite the standards (FIPS 180-4, RFC 8032).

3. **It cannot prove the hardware is correct.** A TPM is a hardware root of trust, but it is not a *proven* root of trust unless the TPM itself is formally verified. The tool should be honest about this: the proof is *conditional on the TPM behaving correctly*, and the TPM's certification (Common Criteria, FIPS 140-3) is the external evidence for that assumption.

The strength of the tool is not that it proves the impossible. It is that it **makes the assumptions explicit, the TCB small, and the evidence independently verifiable** — which is what a court actually needs.
