The integration and interoperability layer is where LexLean's formalization becomes **consumable** — where downstream systems (compliance checkers, legal-tech platforms, regulator dashboards) can query the formal core, receive verifiable proofs or certificates, and replay them without trusting the producer. The UOR Foundation's approach treats integration not as an afterthought but as a **contractual boundary**: the `prism` standard library is itself a façade that re-exports the `uor-foundation` substrate together with the Layer-3 sub-crates, so application authors depend on `uor-prism` alone. For LexLean, this means building three complementary service surfaces and a façade that follows the same architectural discipline.

## 1. JSON-RPC / gRPC Interface to the Lean Runtime

### Why a service interface, not a library

A downstream compliance checker cannot embed the entire Lean 4 toolchain and Mathlib dependency graph. It needs to **submit a query** — a legal scenario, a proposed derivation, a theorem statement — and receive a **proof object or certificate** that it can verify independently. The Kimina Lean Server demonstrates the concrete pattern: it serves the Lean REPL using FastAPI, supports parallelization to check Lean 4 proofs at scale, and exposes a RESTful API where clients submit proof objects and receive verification results. The server can be launched as a Docker container, and a Python SDK simplifies interaction.

Lean 4's own LSP infrastructure provides the lower-level mechanism. The LSP is based on JSON-RPC, a simple protocol that encodes argument and output data as JSON. To mark a Lean procedure as remotely callable, one annotates it with `@[server_rpc_method]`; the procedure must be of type `A → RequestM B`, where `RequestM` is a monad with access to server state and `A`, `B` are JSON-serializable types. Serialization routines are autogenerated via `deriving ToJson, FromJson` or `deriving RpcEncoding`. This means LexLean can expose its core operations — certificate checking, derivation tree validation, axiom auditing — as `@[server_rpc_method]` procedures that any JSON-RPC client can invoke.

For a production-grade interface, LexLean should support both protocols:

**JSON-RPC** for lightweight query/response interactions: submit a legal scenario, receive a certificate or a counterexample. The payload would include the scenario (structured as a `LegalSource` or a derivation request), the target theorem, and the policy context. The response would include the certificate (serialized `DerivationTree`), the axiom profile, and the provenance chain entry.

**gRPC** for streaming and high-throughput interactions. The `lean-grpc` library provides a pure Lean 4 gRPC stack (HTTP/2 + HPACK + protobuf) on `Std.Async`, with a compile-time `Proofs` library covering pure codecs and `H2.ConnState` transitions. The library's guiding principle is "prove the pure layers first" — codecs and connection-state transitions before IO — and it explicitly states that OpenSSL and zlib helpers remain a trusted TCB, with proofs covering the Lean wire model above them. The `lean-tee` project demonstrates a production use case: it exposes `lean-grpc` APIs for "portable integrity TEE compute for open systems — measured guests, hashed receipts, and lean-grpc APIs so anyone can accept honest public results or cheaply reject forged ones".

A LexLean gRPC service would expose streaming methods for:

- **Certificate verification streams**: submit a stream of certificates, receive a stream of verification results (each with an axiom audit and a scope record).
- **Derivation tree replay**: submit a compact certificate, receive the reconstructed derivation tree and the kernel's acceptance verdict.
- **Axiom audit queries**: submit a theorem name, receive the `#print axioms` output and a compliance verdict against the permitted axiom set.

### The trust boundary at the service interface

The service interface introduces a **trust boundary**: the client must be able to verify that the response was produced by the Lean kernel, not by a malicious server. The solution is **proof-carrying responses**: every certificate returned by the service includes the proof object itself, not merely a boolean verdict. The client can then replay the proof against its own pinned Lean environment. The `eigenius` pattern treats "the proof term's content hash, combined with the environment hash and the FFI hash" as the cache key for verification results. For LexLean, the service response would include:

```json
{
  "verdict": "accepted",
  "certificate": { ... },  // serialized derivation tree
  "proof_term_hash": "sha256:...",
  "environment_hash": "sha256:...",
  "axiom_profile": ["propext", "Classical.choice", "Quot.sound"],
  "ledger_entry": "sha256:...",
  "replay_instructions": "lake env lean --run Replay.lean"
}
```

The client does not trust the `"verdict"` field. It trusts the proof term, which it can re-check against its own pinned environment. This is the operational meaning of "proof-carrying responses": the response carries the evidence needed for independent verification.

## 2. WASM Build of Executable Fragments

### Why WASM, not a native binary

A browser-based legal reasoning tool — a compliance checker embedded in a web application, a regulator's dashboard, a legal-tech platform's client-side validator — cannot require users to install the Lean toolchain. A WebAssembly build of the executable fragments solves this: the Lean code compiles to WASM, runs in the browser with deterministic behavior, and communicates with the JavaScript host via a narrow FFI boundary.

The Lean-Rust architecture demonstrates the concrete pattern: a reimplementation of the Lean 4 theorem prover in Rust, designed for "Full browser-based execution with deterministic behavior" and "Import and verify subset of existing Lean 4 code". The architecture includes a `leanr-wasm/` crate for WebAssembly bindings and a `leanr-compat/` crate as the Lean 4 import layer. The trusted computing base is minimal: "the proof kernel is the only trusted component (<1000 LOC)" and "no term enters the environment without kernel verification".

For LexLean, a WASM build would expose a **narrow, auditable API**:

```javascript
// Load the LexLean WASM module
const lexlean = await LexLeanWasm.load();

// Submit a legal scenario and receive a certificate
const certificate = lexlean.verifyScenario({
    scenario: scenarioJson,
    theorem: "LexLean.Contract.duress_voidable",
    policy: "core"
});

// The certificate includes the proof object and the axiom profile
const isValid = lexlean.replayCertificate(certificate);
```

The WASM module would include only the **executable fragments** of LexLean: the derivation checker, the certificate serializer/deserializer, the axiom auditor, and the kernel-verified proof checker. It would *not* include the full elaborator, the tactic framework, or Mathlib. The fragments would be extracted from the Lean build using `@[export]` annotations, which produce C-callable entry points that Emscripten or `wasm-bindgen` can wrap.

### The boundary verification requirement

The critical constraint is that the WASM build must be **boundary-verified**: the FFI between JavaScript and the WASM module must not introduce unsoundness. The Lean-Rust architecture handles this by keeping the kernel as a pure, hash-consed, arena-allocated component with no garbage collection and explicit lifetime management. The WASM bindings are a thin layer over this pure core.

For LexLean, the boundary-verification requirement means:

- **Every exported function must have a Lean-side specification** that states what it computes.
- **The FFI boundary must be type-safe**: the JavaScript types must correspond to the Lean types via a verified serialization schema.
- **The WASM module's axiom profile must be audited**: the compiled WASM should carry the same axiom profile as the Lean source, and the client should be able to verify this by inspecting the embedded audit report.

## 3. Replay Façade for Independent Verifiers

### What a replay façade is

A replay façade is a **minimal verification surface** that lets an independent verifier reconstruct and re-check a proof from a compact certificate without trusting the producer. The `prism_verify` crate in the UOR ecosystem is the concrete template: it is the "Replay façade for verifiers (wiki ADR-005)". The architectural principle is separation of concerns: the certificate producer constructs the evidence, and the checker is "simple, deterministic, and independently re-runnable".

The EULER framework describes the independent replay workflow: "The independent verifier recompiles a Lean 4 project or runs a deterministic checker in an isolated environment. It reads the registered source files, dependencies, tool versions, and inputs, but not the generator's judgment that the run succeeded." The Lean workflow has three stages: premise retrieval, candidate generation, and independent replay. "Retrieval results guide exploration, the generator submits a candidate, and only the replay result enters the machine axis".

### The LexLean replay façade design

A LexLean replay façade would be a **Lean 4 executable** that accepts a compact certificate and performs three phases:

**Phase I: Certificate deserialization.** The facade reads the certificate (a serialized `DerivationTree` or a proof term) and reconstructs the formal object. The deserialization is deterministic and type-safe: the certificate format is a Lean inductive type with a verified decoder.

**Phase II: Specification replay.** The facade re-checks the certificate against the formal specification. For a derivation tree, this means re-running the derivation checker: does every inference step match a registered derivation rule? Does the tree's conclusion match the claimed theorem statement? The EULER replay verifier "executes three phases... return false if any check fails" and "processes the ledger row by row in topological order, performing only integer comparisons at each step".

**Phase III: Axiom audit.** The facade runs `#print axioms` on the reconstructed proof term and asserts that the axiom profile is a subset of the permitted set `{propext, Classical.choice, Quot.sound}`. It also checks for `sorry`, `admit`, newly introduced axiom declarations, and unregistered modules. The audit produces a **verification record** with a common format: record identifier, claim version, checker identity, environment, input hash, result code, scope, axioms used, generated artifacts, and time cost.

### The replay façade as a governance artifact

The replay façade is not merely a technical component. It is the **enforcement mechanism** for LexLean's governance policy. The governance layer (from the previous expansion) encodes admission rules as Lean-checkable predicates. The replay façade executes those predicates against a submitted proof. If the proof fails the predicates — because it uses an undeclared axiom, because its citation is stale, because its derivation tree is malformed — the façade returns a structured rejection with the specific predicate that failed.

This makes the governance policy **operational**: it is not a document that humans interpret; it is a Lean-checkable predicate that the replay façade mechanically evaluates. Any downstream consumer can run the façade themselves and verify that LexLean's claims meet LexLean's own governance standards.

## 4. Align with the Prism Standard Library

### The Prism façade pattern

The `prism` repository states its architectural commitment explicitly: "Per wiki ADR-031, `prism` IS the standard library: a façade re-exporting the `uor-foundation` substrate together with the Layer-3 sub-crates that contribute the built-in axes and built-in types it surfaces". The cargo package table shows the structure: `uor-prism` is the "Standard-library façade. Re-exports foundation + SDK macros + every Layer-3 sub-crate". Application authors "depend on `uor-prism` alone — every standard-library axis and SDK macro is reachable through `use prism::*`".

The architectural rationale is **dependency minimization**: downstream consumers depend on a single façade crate rather than tracking individual sub-crate versions. The façade also enforces a **normative interface**: "Every public item in this codebase backlinks to the wiki section that defines it; the rustdoc surface forms the C4 view of the system. Wiki backlinks are mechanically validated in CI by the workspace tool at `tools/wiki-link-check` — a broken anchor fails the build".

### A `lexlean` façade for the Lean 4 ecosystem

LexLean should mirror this pattern with a `LexLean` façade module (or a `lexlean` Lake package) that re-exports:

- **The substrate types**: `LegalSource`, `Norm`, `Derivation`, `Certificate`, `LegalCitation`, `ValidatedRule`.
- **The DSL surface**: the legal DSL syntax categories, elaborators, and pretty-printers.
- **The verification API**: the certificate checker, the replay façade, the axiom auditor.
- **The governance predicates**: `AxiomCompliant`, `Admissible`, `moduleTrust`, `permittedAxioms`.
- **The skeleton registry**: the `SkeletonEntry` type and the `lexleanRegistry` list.

A downstream consumer would then write:

```lean
import LexLean

open LexLean

-- Everything is reachable through a single import
#check duress_voidable
#check checkCertificate
#check Admissible
#check lexleanRegistry
```

This reduces integration friction: the consumer does not need to know which module contains `checkCertificate` or which sub-package defines `Admissible`. The façade is the **normative interface**, and the CI enforces that every public item in LexLean is reachable through it.

### The façade as an architectural commitment

The Prism façade is not merely a convenience re-export. It is an **architectural commitment**: the façade's structure is defined by ADR-031, and any deviation from the commitment is a governance violation. For LexLean, the analogous commitment would be:

**LexLean ADR-001: The LexLean façade is the normative interface.** Every public item in LexLean must be reachable through `import LexLean`. The façade re-exports the legal core, the DSL surface, the verification API, and the governance predicates. Any item that is not reachable through the façade is, by definition, not part of the public contract.

This commitment has three concrete consequences:

1. **Downstream consumers depend on `LexLean` alone**, not on individual modules. This eliminates version skew: when a sub-module changes, the façade version changes, and the consumer knows to update.
2. **The façade's API surface is the governance surface.** If a predicate is not re-exported by the façade, it is not part of the admission rules. This prevents "hidden governance" — rules that are enforced by internal modules but not visible to external consumers.
3. **The façade is CI-enforced.** A tool analogous to `wiki-link-check` verifies that every public item is reachable through the façade, and a broken link fails the build.

## Summary: The Integration Layer as a Service Contract

| Component | What it provides | Trust boundary |
|---|---|---|
| **JSON-RPC / gRPC service** | Query/response and streaming access to the Lean runtime | Proof-carrying responses; client replays the proof against a pinned environment |
| **WASM build** | Browser-based legal reasoning without the Lean toolchain | Boundary-verified FFI; narrow, audited API surface |
| **Replay façade** | Independent verification from a compact certificate | Deterministic checker; three-phase replay (deserialize, spec-replay, axiom audit) |
| **Prism-aligned façade** | Single-import normative interface | CI-enforced reachability; façade structure is an ADR commitment |

The integration and interoperability layer is not an add-on to the formalization. It is the **contract** between LexLean and its consumers. The service interfaces make the formal core accessible; the replay façade makes it independently verifiable; the Prism-aligned façade makes it architecturally coherent with the UOR ecosystem. Together, these four components transform LexLean from a self-contained formalization into a **consumable, verifiable service** — one where a compliance checker can query the formal core, receive a proof-carrying response, and replay the proof without trusting a single line of LexLean's server code.
